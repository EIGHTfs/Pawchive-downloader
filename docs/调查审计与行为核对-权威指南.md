## 组 A 上游调研与审计

### A1 KToolBox 全量审计报告（来源：KToolBox审计报告.md）

**审计信息**：2026-09-29 对 GitHub Ljzd-PRO/KToolBox master 分支完整 clone（`.probe-ktoolbox/`，pyproject.toml 版本 v1.1.0-beta.1）做静态审计——通读核心源码约 2.06 万行 Python + 抽查前端/测试/文档；本机 Python 3.8.15 低于要求的 3.10，**未实测运行**，运行类结论均标注。审计背景：将 KToolBox 能力转写/对照到本仓库 Node 项目（cli.js 已实现下载/去重/索引；计划自建 Node 后端 + 复用 KToolBox WebUI 前端）。

**总体印象**：工程化程度远超一般开源下载器（类型标注完整、351 个测试、覆盖率门槛 85%、文档多语言同步、安全设计认真：Argon2/CSRF/限流/路径穿越/SSRF 防护）；但体量过大、依赖过重、多个重功能处于 beta 未验证状态，作为转写蓝本需大量裁剪。

### A3 KToolBox 转 Node.js 项目分析报告（来源：KToolBox-nodejs-分析报告.md）

**分析信息**：2026-09-30 只读分析（未改任何代码）。来源 github.com/Ljzd-PRO/KToolBox（master @ e17249be，474 文件，clone 至 `.probe-ktoolbox/`）。

**一、项目概况**：KToolBox 是 Pawchive 站（pawchive.pw）公开作品下载器：WebUI + CLI + Python 客户端三合一。作者 Ljzd-PRO，Python 3.10–3.14，MIT。功能：创作者下载/同步、任务计划（cron）、命名模板、过滤/屏蔽、断点续传、重试、TPS 限速、本地存储桶（bucket）复用、查重跳过。WebUI：React + TypeScript，Playwright e2e，内置 MCP 服务。v1 新版本；Kemono 已不可用，默认走 Pawchive 镜像。

**二、核心架构与下载链路（实测）**：

```
PawchiveClient (Python httpx) → https://pawchive.pw/api/v1
  ├─ list_creators / list_recent_posts / get_creator_profile / list_creator_posts / get_post / search_file_by_hash ...

Downloader (httpx stream) → file.pawchive.pw/data/...
  ├─ Range: bytes={temp_size}- → 断点续传（.tmp 后缀）
  ├─ tenacity 重试（retry_times/retry_interval）
  ├─ TPS 限速（asyncio.sleep(1/tps_limit)）
  ├─ 查重（本地文件 + bucket 复用）
  └─ 进度观察者（DownloadProgressObserver）
```

### B1 Node 后端 vs Python 原版行为区别（来源：行为区别-Node-vs-Python.md）

**研究信息**：2026-09-29 独立代码研究：只读两侧实际代码（Node：cli.js / core.js / adapters/KToolBox-webui.js / server.js；Python：docs/.probe-ktoolbox/ktoolbox/ 下 webui、downloader、api、job、sync、auto_sync），逐项比对行为差异。代码证据格式：`文件:行`（相对本仓库根；Python 侧相对 docs/.probe-ktoolbox/ktoolbox/）。未修改任何代码。

**逐项对比**：

**1. 任务创建去重**：Python 原版先做双重去重——spec 级精确查重（`task_store.py:119-128` create 调 find_duplicate；`:162-171` 按 `spec_json = ? AND status IN (ACTIVE_TASK_STATUSES)`（queued/blocked/running/pause_requested/stop_requested）查库，命中抛 DuplicateTaskError → 路由层 HTTP 409 + `{"message","existing_task_id"}`）；资源冲突调度（`task_scheduler.py:39-44` TaskResources.conflicts_with：output 路径重叠且帖/作者有交集 → `:192-204` 标 blocked + blocked_by）。我们 Node 无去重：POST /tasks 直接 `core.createTask`（无条件 INSERT）+ downloadTask 立即执行恒返回 201；blocked 状态在 TASK_STATUS 存在（core.js:146）但无人设置。影响：重复创建同作者/同帖任务 Python 409 拒绝，Node 照单全收 → 重复下载、同一 .tmp/正式文件被同时写（文件写竞态/损坏风险）。建议：adapter/core 加 spec 精确查重（active 状态）→ 409 + existing_task_id；可选资源冲突 blocked 调度。

**2. 任务控制/取消（stop/pause/resume/rerun）**：Python 原版真中断——先写 pause_requested/stop_requested 再 `running.task.cancel()` 真取消 asyncio 任务，取消级联到下载器（executor → stream.py worker.cancel → downloader chunk 循环检查 self._stop 抛 CancelledError），当前文件被中断、.tmp 保留供续传。我们 Node 只改状态标记——run/stop/pause/resume/rerun 全走 core.updateTaskStatus（仅 UPDATE 状态字段），cli 下载链无任何 abort 通道（streamOnce 的 abortCtl 只用于慢速退避）。后果：①点 stop/pause 状态变但下载继续跑；②下载完成后 core.js:296 无条件覆盖 stopped/paused 为 completed；③rerun → queued 但无调度器永不重跑；④resume → running 无实际作用。建议：AbortSignal/取消令牌贯穿 downloadTask→downloadAuthor→downloadFile→streamOnce（中断 curl 子进程保留 .tmp）；rerun 需要任务队列调度器。

**3. 任务进度统计字段（TaskProgress）**：Python 原版字段全集（task_models.py:194-206：queued_files/processed_files/completed_files/existing_files/failed_files/transferred_bytes/total_bytes/speed_bps/eta_seconds/active_creators/active_downloads/waiting_retries）——transferred_bytes 累计（断点续传起始补差 `+= max(completed-previous_completed,0)`、每次 chunk `+= amount`）；total_bytes 已知文件 total 累计（出现未知 total 置 None）；speed 5s 滑动窗口差分、空闲 1.5s 清 0；eta=(total-transferred)/speed；终态清 active_creators/active_downloads/waiting_retries、speed=0、eta=0/None（task_store.py:512-518）。我们 Node（core.js:248-273 progressReducer）：transferred_bytes = `Math.max(prev, d.size)`（当前最大单文件瞬时 doneBytes，非累计）→ 任务真实累计流量远大于显示值；total_bytes 恒 null；eta_seconds 恒 null；speed_bps 直接覆盖 d.speed（单文件瞬时）；active_downloads 只由 job.progress 写入、job.downloaded/existed/failed 不清除 → 完成后残留旧条目。影响：任务详情/列表「已传输」严重偏小、「总字节/ETA」永远 "—"、完成后「活动下载」残留。建议：transferred 改累计、total 累计已知 size、speed 滑动窗口、任务终态清 active_downloads/speed=0。

**4. 下载执行形态（并发模型/串行/同文件锁范围）**：Python 文件级 worker 池（DownloadWorkerPool N worker 共享 httpx 连接池，从 FairJobQueue 每 creator lane 轮询取文件 job——同帖多文件可并行；sync 任务 creator 级并发信号量 + 文件级池）；任务间 TaskScheduler max_concurrency 上限 + 冲突 blocked——跨任务不会同时下同作者/同帖；同文件 in-flight 防护靠实例锁 _finished_lock + bucket 去重 + 任务级冲突调度。我们 Node 帖子级 worker 池（downloadAuthor 同时最多 concurrency 个帖子并行、每帖内文件串行 inPostConcurrency:1、帖启动间隔 postInterval）；in-flight 锁=每帖一个独立 Map ——只防单帖内同 URL 重复，不跨帖不跨任务；任务间无全局并发上限、无冲突调度（core.downloadTask 各自独立跑，并发 N 任务即 N×concurrency）。影响：①单帖任务 Node 帖内串行=实际并发 1 vs Python 文件级并行；②Node 跨任务同作者/帖无保护 → 同一 .tmp/正式文件被两任务同时写；③无全局任务并发闸。建议：同文件锁提升为跨任务共享（进程级 in-flight Map 键=serverPath）；可选文件级 worker 池；任务级并发上限与冲突调度。

**5. 断点续传**：Python（downloader.py:258-351）：.tmp 临时文件 → stat temp_size → 请求 `Range: bytes={temp_size}-` → 显式处理 200/206（200 时 temp_size=0+删 temp 从头重写；非 206 直接失败；Content-Range 尾段解析 total）→ append 写 → 完整性断言（temp 实际字节≠total → GeneralFailure 重试，temp 保留）→ rename 落盘；无 fsync。我们 Node（cli.js:702-850 downloadFile + 861-903 streamOnce）：.tmp 后缀 PAWCHIVE_TEMP_SUFFIX || '.tmp' → stat .tmp 得 tempSize → `curl -C {tempSize}` 由 curl 处理 Range/200（200 时从头覆盖重写）→ downloadFile 完整性校验（Content-Length/预期大小比对、376B 反爬占位、404 页特征）→ rename 落盘；无 fsync。差异影响：机制基本对齐；细微差别——Python 完整性失败保留 .tmp 重试，Node 反爬占位/大小不符删除 .tmp 重试；Python 用 Content-Range 拿 total（Node 用 Content-Length/API size）。结论：行为已等价，无需强制对齐；可选补显式 206/200 分支与 fsync。

**6. 硬链接去重（同 serverPath 多位置）**：Python 去重判据=目标路径存在即跳过（duplicate_file_check，无大小比对——损坏文件存在也会被跳过）；跨位置复用靠 use_bucket 桶（server_path 本身即 hash 路径，bucket 文件存在 → os.link(bucket, local) 硬链接；下载完成 os.link(temp, bucket) 写桶——链接源=bucket 桶文件全局跨作者复用）。我们 Node：去重索引 buildHashIndex 扫描该作者全部账号目录的 pawchive-index.html files 记录 → Map<serverPath,{rel,size}>（键是 serverPath 非内容 hash）；下载流程 downloadWithDedup：目标已存在+大小一致 → exists 跳过；大小不符 → 删旧重下（Node 有 Python 没有的损坏自愈）；in-flight 同 URL 等待首个完成；记录 rel 存在 → linkOrCopy 硬链接复用；linkOrCopy 硬链接失败（跨卷/NFS）回退 copyFile；链接源=扫描中最后写入记录的目录（遍历顺序依赖、非确定性）。差异影响：①Node 无 bucket → 首次下载后其他作者目录想复用同一文件只能再扫该作者目录（跨作者不复用；Python bucket 全局复用）；②Node 大小比对自愈（Python 损坏文件永久跳过）；③Node 链接源选择依赖目录遍历顺序。建议：跨作者复用可引入全局 bucket（可选）；保留大小比对；链接源按「存在+大小匹配」显式择优。

**7. .tmp 残留清理**：Python 基本不清——中断保留（CancelledError 无 except 清理）、4xx 失败不删、完整性校验失败不删；仅 200 响应（服务端忽略 Range）时删 temp → 永久性失败（如 404 链接）的 .tmp 一直留在磁盘。我们 Node 中断保留、异常内容清理——中断/重试/慢速退避保留 .tmp 供续传；但 4xx/404（curl_exit_22）删 .tmp、反爬占位删 .tmp、缩略图回退失败删 .tmp；成功 rename。差异影响：两边中断都留 .tmp（正常续传，不构成 bug）；区别在无效内容：Node 清 404/占位 .tmp，Python 残留（磁盘垃圾+下次任务 stat 到无效 temp 仍发 Range）。结论：Node 行为已优于 Python 无需对齐；可加可选「启动时清理超过 N 天的 .tmp」。

**8. auto-sync（计划触发查重 + 增量窗口）**：Python 双重查重+增量窗口——计划到期 _trigger_due_plans 先查 active_run（同计划已有 active run → mark_skipped 不重复触发），无才 _enqueue；手动 run_now 对 active run 带 task_id 抛 AutomaticSyncConflictError → HTTP 409 + `{"message","current_task_id"}`；_enqueue 再经 task_scheduler.create 的 spec 查重；增量窗口 _window 用 checkpoint（上次成功位置 - 24h overlap）限定帖子时间范围避免全量。我们 Node 无查重无增量——triggerAutoSyncPlan 遍历 plan.creators 直接 createTask+downloadTask（.catch 吞错），无「同计划是否已在跑」检查；startAutoSyncScheduler 每分钟 tick 到期即触发、不检查上次任务是否完成；adapter run 端点直接 trigger 返回 200（无 409）；无 checkpoint，每次触发全量 fetch 作者列表+全量扫描（下载阶段靠文件级去重跳过）。影响：①计划到期时上次任务未完成 → Node 再建新任务真实发起下载；②手动 run 无 409 告知已在跑；③每次全量拉取。建议：加计划级 active-run 查重（同 plan 有运行中任务则跳过/409 + current_task_id）；spec 级查重随第 1 项；可选 checkpoint 增量窗口。

### B5 帖子请求间隔-设计核查（来源：帖子请求间隔-设计核查-2026-09-29.md）

**结论先行：「帖子请求间隔（秒）」是错误设计**——已有 `PAWCHIVE_TPS` 的 `tpsGate`（slotMs = 1000/tps，唯一正确的等待时间）承担请求节流；`PAWCHIVE_POST_INTERVAL` 是与它功能重叠的多余配置，**Python 原版没有这个配置**，且它会叠加拖慢下载。建议废弃。

**1. 配置项（来源）**：环境变量 `PAWCHIVE_POST_INTERVAL`（默认 5，秒）；config schema 字段 `job.post_interval`（adapters/KToolBox-webui.js:214，label「帖子请求间隔（秒）」description「Pawchive API 单帖间隔（限流）」）；CLI 参数 `--post-interval N`（cli.js:1906）；cli 配置 postIntervalDefault = Number(env) || 5（cli.js:89）；创建任务传入 postInterval = Number(env) || 5（adapter:564）→ core.downloadTask 默认 postInterval=5（core.js:290）。

**2. 前端消费点**：前端没有硬编码该字段——ConfigurationPage 通用渲染 GET /config/schema 的 schema.fields（含 job.post_interval）→ 用户保存 PATCH /config/dotenv/dotenv 传 {values:{PAWCHIVE_POST_INTERVAL}} → adapter 写 .env → cli 下次启动读入 CONFIG.postIntervalDefault。

**3. 后端消费点（帖启动间隔）**：cli.js:1821-1838 downloadAuthor 帖启动循环——槽位未满（下载快于启动）且 i>0 时每新帖启动（getPost 详情请求）前额外 `sleep(postInterval * 1000)`（cli.js:1838）——在 TPS 节流之外叠加。

**4. 已有且正确的节流：tpsGate（cli.js:550-555）**：`slotMs = 1000 / CONFIG.tps`；`waitMs = max(0, lastRequestAt + slotMs - now)`（用户给的公式，唯一正确的等待时间）。消费点：每次建连前调用（cli.js:783 downloadFile 等）——覆盖 API 与下载连接。PAWCHIVE_TPS 默认 1（cli.js:86）；Python 原版等价：DownloaderConfiguration.tps_limit（configuration.py:111 默认 5.0）+ downloader.py:258-259 wait_lock + sleep(1/tps_limit)——同一 slotMs=1000/tps 语义。

**5. Python 原版对照（无此配置）**：原版 configuration.py:202-261 JobConfiguration 完整字段：count / creator_concurrency / include_revisions / allow_list / block_list / extract_content / extract_content_images / extract_external_links / external_link_patterns / keywords / keywords_exclude / download_file / download_attachments / min_file_size / max_file_size——**没有 post_interval 任何字段**。原版请求频率控制 = tps_limit（连接级）+ creator_concurrency（作者级并发）+ config.job.count（下载并发）——没有「每帖固定间隔」概念。→ PAWCHIVE_POST_INTERVAL 是我们自创、原版没有的配置（前端 schema 也由此多一个原版没有的字段）。

**6. 问题（用户论点验证）**：①功能重叠：请求间隔已由 tpsGate 严格保证，postInterval 是叠加上去的第二层等待 ②叠加拖慢：tps=1 时帖启动实际等待 ≈ max(5s, 1s)=5s+；用户把 tps 调到 5 想 5 req/s，postInterval=5 仍把 getPost 限制在 0.2 req/s——**破坏了 TPS 配置语义** ③粒度更粗：postInterval 只作用于帖启动（getPost）、tpsGate 作用于每次建连 ④原版无此概念：契约/行为层面多一个原版没有的配置项。

**7. 建议**：①废弃 PAWCHIVE_POST_INTERVAL / job.post_interval / --post-interval：删除 config schema 字段（adapter:214）、创建任务传参（adapter:564、core.js:290 默认）、downloadAuthor 帖间 sleep（cli.js:1838，槽位未满不再额外 sleep）②请求节流完全交给 PAWCHIVE_TPS（tpsGate）——slotMs=1000/tps 是唯一正确的等待时间 ③若担心 getPost 连发（详情解析），正确做法是把 getPost 请求也纳入 tpsGate（需确认：tpsGate 目前在 downloadFile 建连前调用；apiRequest（fetch）未过 tpsGate——可评估把 API 请求也纳入或维持现状——但不引入固定秒数的帖间隔）④保留并发控制：PAWCHIVE_CONCURRENCY（帖级 worker 池）承担「同时几个帖子在跑」，节流交给 TPS——两个正交，不需要第三个「帖间隔」维度。

**二、「已传输 0 B」怎么来的（bug 链——cli 事件字段名错）**：①前端读 task.progress.transferred_bytes（TasksPage.tsx:913）→ formatBytes(0) → 「0 B」②后端 progressReducer 增量逻辑：`if (typeof d.size === 'number') { p.transferred_bytes += max(0, d.size - (lastSizes[fn]||0)) }`（core.js:367）——只认事件里的 size 字段 ③cli job.progress 事件 emit：`size: p.size ?? null`（cli.js:1645/1795 两处 worker 相同）④p 是 downloadFile 的 onProgress 回调参数对象：`{ filename, doneBytes, total, percent, speed }`（cli.js:802-807 与 905-906 完成事件）——对象里没有 size 字段（字节在 doneBytes）⑤→ 事件 size 恒 null → progressReducer 的 transferred 增量分支永不执行 → transferred_bytes 恒 0（即使文件已下载完成）⑥佐证：DB 里 active_downloads 条目 size:null（core.js:369 存 d.size）与 transferred_bytes:0 吻合。**修复**：cli.js 两处 emit 改 `size: p.doneBytes ?? p.size ?? null`（或后端 progressReducer 改读 d.doneBytes）。一行级修复。

**三、「932 MiB」怎么来的（total_bytes 累计和）**：①前端读 task.progress.total_bytes → formatBytes(977174465) ≈ 932 MiB ②后端：jobTotals[fn] = d.totalSize; p.total_bytes = Σ jobTotals（core.js:368）③cli job.progress emit：totalSize: p.total ?? null——p.total = effectiveTotal = total || probeTotal（html 记录/API size 或 curl Content-Length；下载完成事件 total=result.totalSize，cli.js:905-906）——有值 → total 正常累计 ④该任务 DB：total_bytes:977174465（已完成 4 个文件的 totalSize 之和——completed_files:4）；active_downloads 里 totalSize:null 的文件（进行中、无 expected 记录）不计入 ⑤语义：total_bytes = 「已出现过 job.progress 的文件大小之和」（非任务全部文件总大小）——部分进行中文件暂不计入，任务推进中会增长。

**五、顺带发现：任务卡 running（调度器 UNIQUE 冲突——2026-09-30 新调度器的 bug）**：现象：task-mun08gxi-ywop6a status=running 但无下载进程、progress 10s 无变化、active_downloads 残留；8790 日志 `[scheduler task-mun08gxi-ywop6a] 执行异常: UNIQUE constraint failed: task_attempts.task_id, task_attempts.sequence`。链路：任务第一次运行 attempt sequence=1（18:23 启动，后被中断 status=interrupted）→ 用户 resume/调度器再次启动 → downloadTask 调 startAttempt(taskId, 1, ...)（core.js:421 固定 sequence=1）→ 与已存在 attempt(sequence=1) UNIQUE 冲突 → startAttempt 在 try 块外（core.js:420-421 在 try 之前）→ 异常直接冒泡（不走 catch）→ `[scheduler] 执行异常` 打印 → 任务状态停留 running（420 已 updateTaskStatus('running')）→ 卡死。原版对照：start_attempt 的 sequence = MAX(sequence)+1（webui/task_store.py:337）——无此问题。修复：startAttempt 的 sequence 改为按任务 MAX(sequence)+1 自增（对齐原版）；且把 startAttempt 移入 try（或异常时 updateTaskStatus('failed')）防卡 running。

**六、结论**：①0 B = cli job.progress 事件 size 字段恒 null 的 bug（emit 用了不存在的 p.size，实际字节在 p.doneBytes）——transferred 增量分支永不执行 ②932 MiB = total_bytes 正常（job.progress 的 totalSize 累计和，已完成文件大小之和）——与 0 B 并存是「total 通了、transferred 断了」的 bug 组合 ③两开关：原版 save_creator_indices/download_file 真实生效；我们创建 spec 丢弃两字段、cli 不消费——恒「写索引+下封面」④卡 running：调度器时代 startAttempt 固定 sequence=1 + try 外 → 重跑任务 UNIQUE 冲突 → 卡死。

**1. Strangler Fig（绞杀者模式）——渐进替换遗留系统（业界最成熟）**（Martin Fowler 2001 提出、2024 重审）：核心：新系统以旧系统外缘（路由/接口）为起点逐片替换，每一片替换后保持对外契约不变，直到旧系统完全被绞杀。**本项目正是 Strangler Fig**：server.js 路由层 → adapter（KToolBox 契约翻译）→ core（业务）→ cli（下载引擎）——已具备「协议切换兼容层」形态。缺的是「每片替换后契约回归门禁」。

**2. Spec-to-Spec Migration（先迁移规格，再迁移代码）**（luismori.dev）：核心：迁移旧功能时先迁移「规格」：①反向后端旧功能为现状工件 ②转为可评审的行为规格 ③按规格实现新端 ④对新旧端跑同一规格断言。改之前先有「行为真相」，避免凭代码印象猜。**本项目对应**：原版 openapi.yaml + contract-check.js + compare-ktoolbox.mjs（同输入比较两端结构）——已在做；缺的是「每功能迁移前先写行为规格断言」的纪律。

**3. Legacy Backend Without a Big-Bang Rewrite（分阶段渐进，无大爆炸切换）**（abdulahadsiddiqui.com）：核心六阶段：理解（reverse-engineer 真实契约）→ 测试（为现状行为建测试）→ 隔离（新代码独立）→ 替换（逐片切换）→ 观测（新旧对照）→ 删除（清旧路径）。**与本项目对照**：我们的问题正是「跳过理解/测试阶段直接改 + 每改必回归没形成门禁」——`0 B`（cli emit 字段名）、`UNIQUE 冲突`（startAttempt 固定 sequence）、`waiting_retries 恒空`（事件与聚合层断链）都是**改 A 忘 B 的契约漂移**。

**4. Contract-First + Contract Testing（契约优先 + 契约测试）**（Martin Fowler ContractTest；Pact 为微服务契约测试事实标准）：核心：以契约（openapi/接口 schema）为唯一真相；每端改动跑契约校验，两端契约漂移即失败。**本项目**：contract-check.js（19 端点 0 缺字段）已把契约校验做成可跑门禁——建议升级为「提交前必跑 + 失败即拦」（pre-commit/CI 门禁），并配合 compare-ktoolbox.mjs 新旧端同输入对比。

**三、结论与建议（对症「经常出问题」）**：①面板恒空是两个具体断链：waiting_retries（progressReducer 缺 download.retrying case）、active_creators（cli 缺 creator.* 事件 + 聚合层缺 case）——各 1 个 case 的补齐 ②「经常出问题」的模式本质是零散补丁的契约漂移——成熟解法（上述 4 个理论）都指向同一套纪律：以原版行为为真相（Spec-to-Spec）、每改必过契约门禁（Contract-first：contract-check + compare-ktoolbox 提交前必跑失败即拦）、渐进替换+每片回归（Strangler Fig）、先测试后改（Legacy-No-Big-Bang）③直接落地三步（低门槛、高收益）：a)补齐 progressReducer 两个 case（waiting_retries/active_creators）——本调查修复项 b)把 contract-check.js + compare-ktoolbox.mjs + behavior-align.test.js + webapi.test.js 固定为提交前回归命令（README 记录 + 每次提交前跑）c)新增「行为规格断言」：每个修复先写断言（如「transferred 累计」「waiting_retries 填充」「startAttempt sequence 自增」）再改——防改 A 忘 B 复发。

**二、根因**：①主因——server 进程死亡后，其 spawn 的 curl 子进程变孤儿继续下载：我们下载用 spawn(CURL_BIN, ...)（cli.js:873 streamOnce）——Node 的 spawn 子进程不随父进程退出而自动终止。8789 主 server 被停止/替换（进程消失）后，它已 spawn 的帖子下载 curl（19574 等）PPID 变 1 继续下载，直到各自的 --max-time 300 到期（约 5 分钟）或完成——期间用户看到「任务关了还在下」。正常路径（任务 stop/删除 → core.abortTask → controller.abort() → streamOnce 500ms 检查 shouldAbort() → p.kill('SIGTERM')）只在父进程活着时有效；父进程死亡时没有清理者。②次因——abort 不覆盖收尾的头像下载：downloadCreatorAvatars（cli.js:1152-1190 附近）的 streamOnce 固定传 {shouldAbort: () => false}——任务 abort 后 finishDownload → writeCreatorIndex → downloadCreatorAvatars 仍会下载头像（当前 21606 即此场景——8790 任务 abort 后收尾仍在下头像）。③残留说明：中断下载的 .tmp 按设计保留供续传（不是 bug）——用户看到的目录里 .tmp 是孤儿 curl 停止后留下的，已停止增长。

**三、修复建议（按优先级）**：①【核心】进程退出统一清理子 curl（cli.js streamOnce 层）：维护全局 activeCurls Set（spawn 时 add、close/error 时 delete）；process.on('exit') + SIGTERM + SIGINT 钩子统一 kill('SIGTERM') 全部 activeCurls——覆盖正常 stop/重启（kill -9/崩溃仍不触发，需配合 2）②【兜底】server 启动时清扫孤儿下载 curl：启动扫描 /proc/*/cmdline（或 ps）中 `curl ... -o <dataRoot>` 且 PID 非本进程、非本进程子进程的 → kill(pid,'SIGTERM')——覆盖 kill -9/崩溃遗留的上一轮孤儿 ③【补洞】abort 覆盖头像下载：downloadCreatorAvatars 的 streamOnce 改为透传 abortCtl（shouldAbort: () => abortCtl && abortCtl.shouldAbort()）——abort 后跳过头像下载（或由上层判断已 abort 直接返回）④【运维立即】当前已无孤儿 curl（19574 已自行退出）；残留 .tmp 保留（续传基础）；8790 为测试 server——如需停其任务走 API stop（abort 链路有效）或停 8790 server ⑤【语义确认】auto-sync 计划 pause/删除只停未来触发（对齐原版 auto_sync_scheduler.py——active run 照跑）；已运行任务需任务级 stop/删除（我们的 abort 链路有效 ✓）。若用户期望「关同步=停已运行任务」，需额外把计划 pause 级联 abort 该计划起源的任务（当前无 plan→task 关联表，属增强项）。

| 本地已有 + 源站 404（网站删了资源） | [已存在] 跳过——不重下、不删除本地文件 | ✅ 本地资产安全 |
| 本地没有 + 源站 404 | curl -f 拦截 → 一次性失败（不落 404 页、不重试、计入失败清单并列出路径） | ✅ 明确报缺失 |
| 失败文件统计 | 完成行列出完整路径（Akt/【2024 S1】 Spring 春/...） | ✅ 可人工核对 |

**三、实现机制**：①本地已有文件保护：下载前「大小感知检查」——目标文件存在且大小与 html 记录一致 → exists 跳过（不触发下载、不触碰源站）；即使源站已 404，本地文件原封不动 ②源站 404 拦截：curl 带 -f（HTTP 4xx/5xx 直接失败 exit 22），curl_exit_22 为确定性失败不重试、不落 404 页面、不产生 .tmp 残留 ③缺失文件明确报错：失败文件计入完成统计（路径列全），供人工判断（源站已删则永久缺失，可手动补回后重跑自动识别为已存在）。

**四、意义**：「网站没了资源、本地已有」= 本地资产永不因源站删除而丢失/重下（离线归档安全）；仅「本地也缺失」的文件报失败——提示源站删除造成的真实缺口，可人工补档。
