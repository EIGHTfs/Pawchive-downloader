# MCP 接入调研与方案（2026-09-30）

> 调研对象：原版 KToolBox MCP（`docs/.probe-ktoolbox/ktoolbox/webui/mcp_server.py` / `mcp_routes.py` / `mcp_tokens.py` + `webui/openapi.yaml` 的 `x-ktoolbox-mcp` 元数据 + 前端 `webui/src/pages/MCPPage.tsx`）。
> 目标：我们（Pawchive-downloader Node 后端）**接入 MCP 供 AI 使用**——DSH（DeepSeek Harness）本身是 MCP 客户端（`@deepseek-ai/dsh-mcp-client`，stdio 传输，已有 browser-use 实验包先例），因此我们做一个 **MCP server（stdio），把 core.js 业务能力暴露成 MCP 工具**，DSH 的 AI 即可 tools/list 发现、tools/call 调用（建任务/查任务/搜创作者/auto-sync 等）。

---

## 一、原版 MCP 全景（已核实）

### 1. 生成方式：FastMCP.from_openapi（契约驱动）
- `mcp_server.py:37-71`：把 WebUI 的**整个 OpenAPI 契约**（openapi.yaml，带 `x-ktoolbox-mcp` 扩展元数据）喂给 `FastMCP.from_openapi`，自动生成 MCP 工具集；一个 REST operation = 一个 MCP tool。
- `route_map_fn`（`_route_map`，:90-92）：按元数据 `enabled: true` 决定工具纳入/排除 → **38 个启用工具**（`grep -c "enabled: true" openapi.yaml` = 38）。
- `_configure_component`（:95-107）：每工具挂「scope + safety」标签 + ToolAnnotations（readOnly/destructive/idempotent/openWorld）。
- `_mcp_names`（:110-118）：operationId → 工具名映射。

### 2. 工具元数据（`x-ktoolbox-mcp`，openapi.yaml 每个 operation 自带）
| 字段 | 取值 | 含义 |
|---|---|---|
| `enabled` | true/false | 是否暴露为 MCP 工具（38 个 true） |
| `name` | 如 `list_tasks`/`create_task`/`pause_task` | MCP 工具名 |
| `scope` | `mcp:read` / `mcp:write` | 读写权限域（token 鉴权用） |
| `safety` | `read` / `write` / `destructive` | 危险度标注（前端/客户端可据此提示） |
| `openWorld` | bool | 是否外部世界（true=联网类） |

**38 个启用工具分组**（从 openapi.yaml 提取，`operationId`）：
- 配置：config_schema(read)
- 创作者：list_creators(r)、add_creator(w)、update_creator(w)、delete_creator(destructive)
- blockers：list_blockers(r)、replace_blockers(destructive)
- Pawchive 站：search_creators(r)、search_works(r)、post_details(r)、list_work_revisions(r)、get_pawchive_version(r)、creator_avatar(r)
- 任务：list_tasks(r)、create_task(w)、get_task(r)、update_task(w)、delete_task(d)、pause_task(w)、stop_task(w)、resume_task(w)、rerun_task(w)、task_attempts(r)、task_events(r)、cleanup_preview(r)、event_stream(r)
- auto-sync：list_automatic_sync_plans(r)、create_automatic_sync_plan(w)、get_automatic_sync_plan(r)、update_automatic_sync_plan(w)、pause/resume/run_automatic_sync_plan(w)、list_automatic_sync_runs(r)、list_automatic_sync_updates(r)
- naming：get_naming(r)、get_legacy_naming_migration(r)、list_naming_conversions(r)、get_naming_conversion(r)

### 3. 鉴权（token + scope）
- `mcp_tokens.py`：token 形如 `ktmcp_<urlsafe36>`（:61），**只存 SHA-256 digest**（`token_digest`），scope = `mcp:read`（read 权限）或 `mcp:read+mcp:write`（manage 权限，:60）；过期/吊销/last_used 跟踪；创建需确认密码（`mcp_routes.py` confirm_password）。
- `mcp_server.py:18-34` `DatabaseTokenVerifier`：校验 token → 返回 AccessToken（scopes/expires/claims）；每工具挂 `require_scopes(scope)`。
- 内部调用走 ASGI transport 直连 app（`httpx.ASGITransport` + `internal_token` Bearer，:43-48）——**MCP 工具不经 HTTP 网络，直通 FastAPI app**。

### 4. 管理端点（`mcp_routes.py`）
- `GET /api/v1/mcp/status` → MCPStatusResponse（tool_count）
- `GET /api/v1/mcp/tools` → MCPToolResponse[]（name/operation_id/description/category/scope/safety/open_world）
- `GET/POST /api/v1/mcp/tokens`（list/create）、`POST /mcp/tokens/{id}/revoke`
- `GET /api/v1/openapi.yaml`（契约下载）

### 5. 前端 MCPPage
- 显示 status（enabled/running/tool_count）、工具目录（category 分组、scope 过滤、搜索）、token 列表（创建/吊销/复制 endpoint 与 openapi url）；`lib/mcp.ts: mcpReadyConfiguration` 检测端点就绪。

## 二、我们现状（MCP 空对齐）

`adapters/KToolBox-webui.js:660-667`（P1-3 空对齐）：
- `/api/v1/mcp/status` → `{ enabled:false, running:false, tool_count:0, endpoint_path:null, openapi_path:null, transport:null, ... }`（前端显示「未启用」不崩）
- `/api/v1/mcp/tokens` → `[]`、`/api/v1/mcp/tools` → `[]`
- 其余 `/mcp` → 404

即：**前端 MCP 管理页可打开但显示未启用**；真正 MCP 协议能力为零。

## 三、接入方案（供 AI 使用的 MCP server）

### 1. 形态：新增 `mcp-server.js`（stdio 传输，零依赖手写协议）
- DSH 是 MCP 客户端、用 stdio 拉起子进程（`@modelcontextprotocol/client` stdio transport）——我们做一个 **`node mcp-server.js` 子进程**，走标准 MCP JSON-RPC 2.0（`initialize` → `tools/list` → `tools/call` → `ping/notifications`）。
- 零依赖手写（项目纪律：零依赖；MCP 协议只有 `initialize/tools/list/tools/call` 几个核心方法，手写 ~200 行即可，不引入 @modelcontextprotocol/sdk）。
- **复用 core.js**：工具实现直接调 `core.listTasks/createTask/abortTask/listCreators/searchCreators/...`（MCP server 进程内 require core.js，业务内核即 core——不经过 HTTP adapter，避免起 HTTP server）。
  - 注意项目架构纪律：cli.js 是独立下载引擎（禁动）；**core.js 是兼容层业务内核**，MCP server 作为第三个协议面（继 KToolBox-webui HTTP 适配器之后）复用 core 能力——符合「引擎在 cli、业务在 core、协议在 adapter/server」分层。

### 2. 工具面：映射我们的 core 能力（对齐原版 38 个的子集——我们已实现的）
| MCP 工具（对齐原版名） | 实现（core/adapter 现成能力） | scope/safety |
|---|---|---|
| list_tasks / get_task / task_attempts / task_events | core.listTasks/getTask/listAttempts/eventStore.events | read |
| create_task / update_task / delete_task | core.createTask+downloadTask / PATCH spec / abortTask+DELETE | write/destructive |
| pause_task / stop_task / resume_task / rerun_task | core.abortTask+updateTaskStatus / ... | write |
| list_creators / search_creators | core.listCreators / searchCreators | read |
| add/update/delete_creator | core.updateCreatorProfile/deleteCreatorProfile | write/destructive |
| list_automatic_sync_plans / get / create / update / pause / resume / run | core.auto-sync 全套（已真实实现） | read/write |
| get_naming / config_schema | core.getNaming / adapter schema 字段 | read |
| search_works / post_details / get_pawchive_version | core.cli.fetchPostsByUrl/getPost / cli 导出 | read |
| list_blockers / replace_blockers | 空对齐（可暴露返回 []） | read/destructive |
| cleanup_preview | core.previewTaskArtifacts（已实现 delete outputs） | read |

> 取舍：原版 38 个全暴露；我们**先暴露已真实实现的 ~22 个**，naming 转换/legacy-migration/avatar/event_stream 等按需补（event_stream 可后续做 SSE 别名）。

### 3. 鉴权：分级可选
- **DSH 本地 stdio 场景**：AI 直接从本机拉起 `node mcp-server.js`——可无鉴权（类似 dev-noauth）或读 env `PAWCHIVE_MCP_TOKEN` 简单 Bearer 校验（`tools/call` 请求头/参数带 token）。
- **对齐原版**：可选实现 token digest 表 + scope（mcp:read/mcp:write）——但本地 AI 用意义小，**建议 v1 无鉴权 + env 开关**，后续需要再补。
- 与 ktoolbox-mcp 的 open_world 标注：我们是内网本地工具，全 `openWorld:false`。

### 4. 部署/接入 DSH 的两条路
- **A. 手动挂载**（最快验证）：DSH 配置 MCP server `command: node /…/mcp-server.js`（stdio）→ AI 会话里直接有 22 个 Pawchive 工具可用。
- **B. DSH 插件式**（正式）：参考 browser-use-chrome-devtools-mcp 实验包，做一个 dsh 插件 provider 把 `mcp-server.js` 注册进 Session 的 MCP 连接（生命周期/重连/工具注册交给 dsh-mcp-client）——工作量较大，作为后续项。

### 5. 与现有 WebUI 兼容层的关系
- 现有 `server.js + adapters/KToolBox-webui.js`（HTTP）服务**前端交互**；MCP server 服务 **AI 调用**——两者并行，都复用 core.js，不冲突。
- 前端 MCPPage「管理」页可继续显示未启用（页面只读展示），或后续把 `mcp/status` 改为报告 true（当 MCP server 进程存活时）——v1 保持空对齐不动，MCP 能力以独立 mcp-server.js 提供。

## 四、决策点（需确认）

1. **范围 v1**：MCP server 暴露 ~22 个已实现工具（tasks/creators/auto-sync/naming/search）够不够？还是初步先把「任务全套 + creators + auto-sync」做出来（最常用）？
2. **鉴权**：v1 无鉴权（env `PAWCHIVE_MCP_TOKEN` 可选 Bearer）确认？还是对齐原版做 token digest + scope？
3. **接入 DSH**：先手动 stdio 挂载（快）还是直接做 dsh-mcp-client 插件（正式）？建议先 A 后 B。
4. **transport**：仅 stdio（DSH 场景）够吗？是否需要顺带 SSE/HTTP（供远程 AI/Claude Desktop 等）——v1 可只 stdio。
