> 两部分：①「等待重试 / 活动作者」面板恒空的根因（代码实证 + 修复方向）②「经常出问题」的对症：成熟的后端重写理论/示例（Strangler Fig / Spec-to-Spec / Contract-first）与本项目映射。

## 一、「等待重试 / 活动作者」恒空根因（代码实证）

| 面板 | 前端读（源码） | 我们后端现状 | 原版对照 | 根因 |
|---|---|---|---|---|
| **等待重试**（waiting_retries） | `progress.waiting_retries`（TasksPage.tsx:876/962-997） | progressReducer 初始 `waiting_retries: {}`（core.js:348）——**无任何 case 填充/清除**；虽然 cli 已发 `download.retrying` 事件（92cfac9，cli.js:1647/1797），但 **progressReducer 不消费该事件类型** → progress_json 恒空 | 原版 `download_retrying` → `waiting_retries[task_key] = WaitingRetry(...)`（task_reporter.py:165-194），download_started/finished 时 pop（:130/:214） | progressReducer 缺 `download.retrying` case（事件流有、聚合层断） |
| **活动作者**（active_creators） | `progress.active_creators`（TasksPage.tsx:920/927-937） | 初始 `[]`（core.js:348）——无 case 填充/删除；**cli 不发 `creator.started/creator.finished` 事件**（grep cli.js 空） | 原版 `creator_started` append / `creator_finished` remove（task_reporter.py:70-101，由 SyncCoordinator 每作者调用） | cli 无 creator.* 事件 + progressReducer 无 case（两层都缺） |

**修复方向**：
- **waiting_retries**：progressReducer 加 `download.retrying` case——`waiting_retries[filename] = { creator_key, filename, retry_count, status_code }`；`job.downloaded/existed/failed/aborted` 与 `download.started` 时 pop 对应项（对齐原版）。
- **active_creators**：cli downloadAuthor 开始/结束时发 `creator.started` / `creator.finished`（单作者任务即当前作者名）→ progressReducer case append/remove（对齐原版 creator_started/creator_finished 语义）。注意我们 sync 任务按 creator 拆任务，active_creators 实际是「当前下载的 creator」——取 downloadAuthor 的 meta.userId 即可。

## 二、成熟的后端重写理论/示例（「经常出问题」的对症）

### 1. Strangler Fig（绞杀者模式）——渐进替换遗留系统（业界最成熟）
- [Martin Fowler: Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html)（2001 提出，[2024 重审](https://martinfowler.com/articles/2024-strangler-fig-rewrite.html)）
- 核心：**新系统以旧系统外缘（路由/接口）为起点逐片替换**，每一片替换后保持对外契约不变，直到旧系统完全被绞杀。
- **本项目正是 Strangler Fig**：server.js 路由层 → adapter（KToolBox 契约翻译）→ core（业务）→ cli（下载引擎）——已具备「协议切换兼容层」形态。缺的是「每片替换后契约回归门禁」（见下）。

### 2. Spec-to-Spec Migration（先迁移规格，再迁移代码）
- [luismori.dev: Before You Copy Legacy Code — Spec-to-Spec Migration](https://luismori.dev/article/before-you-copy-legacy-code-spec-to-spec-migration)
- 核心：**迁移旧功能时先迁移「规格」**：①反向后端旧功能为现状工件 ②转为可评审的行为规格 ③按规格实现新端 ④对新旧端跑同一规格断言。改之前先有「行为真相」，避免凭代码印象猜。
- **本项目对应**：原版 openapi.yaml（docs/.probe-ktoolbox/webui/openapi.yaml）+ contract-check.js + compare-ktoolbox.mjs（同输入比较两端结构）——**已在做**；缺的是「每功能迁移前先写行为规格断言」的纪律。

### 3. Legacy Backend Without a Big-Bang Rewrite（分阶段渐进，无大爆炸切换）
- [abdulahadsiddiqui.com: Refactoring a Legacy Backend Without a Big-Bang Rewrite](https://www.abdulahadsiddiqui.com/writing/agent-rewrote-my-backend)
- 核心六阶段：**理解（reverse-engineer 真实契约）→ 测试（为现状行为建测试）→ 隔离（新代码独立）→ 替换（逐片切换）→ 观测（新旧对照）→ 删除（清旧路径）**。
- **与本项目「经常出问题」对照**：我们的问题正是「跳过理解/测试阶段直接改 + 每改必回归没形成门禁」——`0 B`（cli emit 字段名）、`UNIQUE 冲突`（startAttempt 固定 sequence）、`waiting_retries 恒空`（事件与聚合层断链）都是**改 A 忘 B 的契约漂移**。

### 4. Contract-First + Contract Testing（契约优先 + 契约测试）
- 权威：Martin Fowler [ContractTest](https://martinfowler.com/bliki/ContractTest.html)；Pact（微服务契约测试事实标准）。
- 核心：**以契约（openapi/接口 schema）为唯一真相**；每端改动跑契约校验，两端契约漂移即失败。
- **本项目**：contract-check.js（19 端点 0 缺字段）已把契约校验做成可跑门禁——**建议升级为「提交前必跑 + 失败即拦」**（pre-commit/CI 门禁），并配合 compare-ktoolbox.mjs 新旧端同输入对比。

## 三、结论与建议（对症「经常出问题」）

1. **面板恒空是两个具体断链**：waiting_retries（progressReducer 缺 download.retrying case）、active_creators（cli 缺 creator.* 事件 + 聚合层缺 case）——各 1 个 case 的补齐。
2. **「经常出问题」的模式本质是零散补丁的契约漂移**——成熟解法（上述 4 个理论）都指向同一套纪律：
   - **以原版行为为真相**（Spec-to-Spec：迁移前先定行为规格断言）
   - **每改必过契约门禁**（Contract-first：contract-check + compare-ktoolbox 提交前必跑，失败即拦）
   - **渐进替换 + 每片回归**（Strangler Fig：我们已是兼容层形态，补上「每步回归」即可）
   - **先测试后改**（Legacy-No-Big-Bang：为现状行为建测试，再动代码）
3. **直接落地三步**（低门槛、高收益）：
   - ①补齐 progressReducer 两个 case（waiting_retries/active_creators）——本调查修复项
   - ②把 `contract-check.js + compare-ktoolbox.mjs + behavior-align.test.js + webapi.test.js` 固定为提交前回归命令（README 记录 + 每次提交前跑）
   - ③新增「行为规格断言」：每个修复先写断言（如「transferred 累计」「waiting_retries 填充」「startAttempt sequence 自增」）再改——防改 A 忘 B 复发。
