## 二、根因

1. **主因——server 进程死亡后，其 spawn 的 curl 子进程变孤儿继续下载**：
   - 我们下载用 `spawn(CURL_BIN, ...)`（`cli.js:873` streamOnce）——Node 的 spawn 子进程**不随父进程退出而自动终止**。
   - 8789 主 server 被停止/替换（进程消失）后，它已 spawn 的帖子下载 curl（19574 等）**PPID 变 1 继续下载**，直到各自的 `--max-time 300` 到期（约 5 分钟）或完成——期间用户看到「任务关了还在下」。
   - 正常路径（任务 stop/删除 → `core.abortTask` → `controller.abort()` → streamOnce 500ms 检查 `shouldAbort()` → `p.kill('SIGTERM')`）**只在父进程活着时有效**；父进程死亡时没有清理者。
2. **次因——abort 不覆盖收尾的头像下载**：`downloadCreatorAvatars`（`cli.js:1152-1190` 附近）的 streamOnce 固定传 `{ shouldAbort: () => false }`——任务 abort 后 `finishDownload → writeCreatorIndex → downloadCreatorAvatars` 仍会下载头像（当前 21606 即此场景——8790 任务 abort 后收尾仍在下头像）。
3. **残留说明**：中断下载的 `.tmp` 按设计**保留供续传**（不是 bug）——用户看到的目录里 `.tmp` 是孤儿 curl 停止后留下的，已停止增长。

## 三、修复建议（按优先级）

1. **【核心】进程退出统一清理子 curl**（`cli.js` streamOnce 层）：
   - 维护全局 `activeCurls` Set（spawn 时 add、close/error 时 delete）；
   - `process.on('exit') + SIGTERM + SIGINT` 钩子统一 `kill('SIGTERM')` 全部 activeCurls——覆盖正常 stop/重启（`kill -9`/崩溃仍不触发，需配合 2）。
2. **【兜底】server 启动时清扫孤儿下载 curl**：启动扫描 `/proc/*/cmdline`（或 ps）中 `curl ... -o <dataRoot>` 且 PID 非本进程、非本进程子进程的 → `kill(pid, 'SIGTERM')`——覆盖 kill -9/崩溃遗留的上一轮孤儿。
3. **【补洞】abort 覆盖头像下载**：`downloadCreatorAvatars` 的 streamOnce 改为透传 `abortCtl`（`shouldAbort: () => abortCtl && abortCtl.shouldAbort()`）——abort 后跳过头像下载（或由上层判断已 abort 直接返回）。
4. **【运维立即】** 当前已无孤儿 curl（19574 已自行退出）；残留 `.tmp` 保留（续传基础）；8790 为测试 server——如需停其任务走 API stop（abort 链路有效）或停 8790 server（其子进程会按建议 1/2 清理）。
5. **【语义确认】auto-sync 计划 pause/删除只停未来触发**（对齐原版 `auto_sync_scheduler.py`——active run 照跑）；已运行任务需任务级 stop/删除（我们的 abort 链路有效 ✓）。若用户期望「关同步=停已运行任务」，需额外把计划 pause 级联 abort 该计划起源的任务（当前无 plan→task 关联表，属增强项）。
