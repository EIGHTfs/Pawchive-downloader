# 帖子请求间隔（秒）设计核查（2026-09-29）

> 结论先行：**「帖子请求间隔（秒）」是错误设计**——我们已有 `PAWCHIVE_TPS` 的 `tpsGate`（`slotMs = 1000/tps`，唯一正确的等待时间）承担请求节流；`PAWCHIVE_POST_INTERVAL` 是与它功能重叠的多余配置，**Python 原版没有这个配置**，且它会叠加拖慢下载。建议废弃。

---

## 1. 配置项（来源）

| 项 | 值 |
|---|---|
| 环境变量 | `PAWCHIVE_POST_INTERVAL`（默认 **5**，秒） |
| config schema 字段 | `job.post_interval`（`adapters/KToolBox-webui.js:214`——label「帖子请求间隔（秒）」、description「Pawchive API 单帖间隔（限流）」） |
| CLI 参数 | `--post-interval N`（`cli.js:1906`） |
| cli 配置 | `postIntervalDefault: Number(process.env.PAWCHIVE_POST_INTERVAL) || 5`（`cli.js:89`） |
| 创建任务传入 | `postInterval: Number(process.env.PAWCHIVE_POST_INTERVAL) || 5`（`adapters/KToolBox-webui.js:564`）→ core.downloadTask 默认 `postInterval = 5`（`core.js:290`） |

## 2. 前端消费点

前端**没有硬编码**该字段——ConfigurationPage 通用渲染 `GET /config/schema` 返回的 `schema.fields`（含 `job.post_interval` 一项）→ 用户在「下载任务」分区看到「帖子请求间隔（秒）」→ 保存 `PATCH /config/dotenv/dotenv` 传 `{ values: { PAWCHIVE_POST_INTERVAL } }` → adapter 写 .env → cli 下次启动读入 `CONFIG.postIntervalDefault`。

## 3. 后端消费点（帖启动间隔）

`cli.js:1821-1838` downloadAuthor 帖启动循环：

```js
// 槽位未满（下载快于启动）→ 帖启动间隔节流 getPost 解析（防 API 连发）
if (active.size >= slotCount) { await Promise.race([...]); }
else if (i > 0) { ... await sleep(postInterval * 1000); }  // cli.js:1838——每新帖启动前固定睡 postInterval 秒
```

即：**每个帖子启动（getPost 详情请求）前额外 sleep postInterval 秒**——在 TPS 节流之外叠加。

## 4. 已有且正确的节流：tpsGate（`cli.js:550-555`）

```js
let lastRequestAt = 0; // 全局 TPS 节流：串行下载时控制每秒连接数
async function tpsGate() {
  const slotMs = 1000 / CONFIG.tps;            // tps=1 → 1000ms
  const now = Date.now();
  const waitMs = Math.max(0, lastRequestAt + slotMs - now);  // ← 用户给的公式，唯一正确的等待时间
  lastRequestAt = now + waitMs;
  ...
}
```

- 消费点：**每次建连前**调用（`cli.js:783` downloadFile 等）——覆盖 API 与下载连接。
- `PAWCHIVE_TPS` 默认 1（`cli.js:86`）；**Python 原版等价**：`DownloaderConfiguration.tps_limit`（原版 `configuration.py:111` 默认 5.0）+ `downloader.py:258-259` `async with self.wait_lock: await asyncio.sleep(1 / tps_limit)`——同一 slotMs=1000/tps 语义。

## 5. Python 原版对照（无此配置）

原版 `configuration.py:202-261` `JobConfiguration` 完整字段：`count / creator_concurrency / include_revisions / allow_list / block_list / extract_content / extract_content_images / extract_external_links / external_link_patterns / keywords / keywords_exclude / download_file / download_attachments / min_file_size / max_file_size`——**没有 post_interval/postInterval 任何字段**。
原版的请求频率控制 = **`tps_limit`（连接级）+ `creator_concurrency`（作者级并发）+ `config.job.count`（下载并发）**——没有「每帖固定间隔」概念。
→ **`PAWCHIVE_POST_INTERVAL` 是我们自创、原版没有的配置**（前端 schema 里也由此多了一个原版没有的字段）。

## 6. 问题（用户论点验证）

1. **功能重叠**：请求间隔已由 tpsGate（slotMs=1000/tps）严格保证——`postInterval` 是叠加上去的第二层等待。
2. **叠加拖慢**：tps=1 时帖启动实际等待 ≈ `max(postInterval=5s, slot=1s)` = 5s+（叠加后比 TPS 语义更慢）；用户把 tps 调到 5 想 5 req/s，`postInterval=5` 仍把 getPost 详情限制在 0.2 req/s——**破坏了 TPS 配置语义**。
3. **粒度更粗**：postInterval 只作用于「帖启动」（getPost），tpsGate 作用于「每次建连」——前者是固定秒数、后者是精确 slot 节流。
4. **原版无此概念**：契约/行为层面多了一个原版没有的配置项（前端「下载任务」分区多一个原版不存在的设置项）。

## 7. 建议

- **废弃 `PAWCHIVE_POST_INTERVAL` / `job.post_interval` / `--post-interval`**：删除 config schema 字段（adapter:214）、创建任务传参（adapter:564、core.js:290 默认）、downloadAuthor 帖间 sleep（cli.js:1838，槽位未满时不再额外 sleep）。
- 请求节流**完全交给 `PAWCHIVE_TPS`（tpsGate）**——`slotMs = 1000/tps` 是唯一正确的等待时间。
- 若担心 getPost 连发（详情解析），正确做法是**把 getPost 请求也纳入 tpsGate**（已在每次建连前调用——实际上 apiRequest 建连也走？需确认：tpsGate 目前在 downloadFile 建连前调用；apiRequest（fetch）未过 tpsGate——可评估把 API 请求也纳入 tpsGate 或维持现状——但**不引入固定秒数的帖间隔**）。
- 保留并发控制：`PAWCHIVE_CONCURRENCY`（帖级 worker 池）承担「同时几个帖子在跑」，节流交给 TPS——两个正交，不需要第三个「帖间隔」维度。
