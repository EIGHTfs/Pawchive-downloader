## 二、「已传输 0 B」怎么来的（bug 链——cli 事件字段名错）

1. 前端读 `task.progress.transferred_bytes`（TasksPage.tsx:913）→ `formatBytes(0)` → 「0 B」。
2. 后端 progressReducer 增量逻辑：`if (typeof d.size === 'number') { p.transferred_bytes += max(0, d.size - (lastSizes[fn]||0)) }`（core.js:367）——**只认事件里的 `size` 字段**。
3. cli job.progress 事件 emit：`size: p.size ?? null`（cli.js:1645/1795 两处 worker 相同）。
4. p 是 downloadFile 的 onProgress 回调参数对象：`{ filename, doneBytes, total, percent, speed }`（cli.js:802-807 与 905-906 完成事件）——**对象里没有 `size` 字段（字节在 `doneBytes`）**。
5. → 事件 `size` 恒 null → progressReducer 的 transferred 增量分支**永不执行** → **transferred_bytes 恒 0**（即使文件已下载完成）。
6. 佐证：DB 里 active_downloads 条目 `size: null`（core.js:369 存 d.size）与 `transferred_bytes: 0` 吻合。

**修复**：cli.js 两处 emit 改 `size: p.doneBytes ?? p.size ?? null`（或后端 progressReducer 改读 `d.doneBytes`）。一行级修复。

## 三、「932 MiB」怎么来的（total_bytes 累计和）

1. 前端读 `task.progress.total_bytes` → `formatBytes(977174465)` ≈ 932 MiB。
2. 后端：`jobTotals[fn] = d.totalSize; p.total_bytes = Σ jobTotals`（core.js:368）。
3. cli job.progress emit：`totalSize: p.total ?? null`——`p.total = effectiveTotal = total || probeTotal`（html 记录/API size 或 curl Content-Length；下载完成事件 total=result.totalSize，cli.js:905-906）——**有值** → total 正常累计。
4. 该任务 DB：`total_bytes: 977174465`（已完成 4 个文件的 totalSize 之和——completed_files:4）；active_downloads 里 `totalSize: null` 的文件（进行中、无 expected 记录）不计入。
5. **语义**：total_bytes = 「已出现过 job.progress 的文件大小之和」（非任务全部文件总大小）——部分进行中文件（无 size 记录）暂不计入，任务推进中会增长。

## 四、创建任务两个勾选（保存作者索引 / 下载主文件封面）两后端处理

| 开关 | 前端（TaskEditor） | Python 原版 | 我们 Node |
|---|---|---|---|
| **save_creator_indices**（保存作者索引） | sync 表单「保存作者索引」→ SyncTaskSpec.save_creator_indices（TaskEditor.tsx:97/173，默认 false） | SyncTaskSpec 字段 → task_executor._sync → SyncOptions → produce_jobs_from_creator（action/job.py:272/292-294）：决定是否记录 CreatorIndices 数据——**真实生效** | adapter POST /tasks 创建 spec 只存 `{kind/service/creator_id/post_id/post/output/dryrun/creators}`（KToolBox-webui.js:589）——**save_creator_indices 被丢弃**；taskRecord 输出层仅响应补字段 `?? false`（:60）；cli 下载**无条件** `writeCreatorIndex` 写创作者索引——**勾选不生效（恒写索引）** |
| **download_file**（下载主文件/封面） | sync 表单「下载主文件」→ SyncTaskSpec.download_file（TaskEditor.tsx:99/175，默认 true） | 同上 → produce_jobs_from_creator（action/job.py:120-121）：`selected_download_file && post.file → 生成封面 job`——**真实生效（可关封面下载）** | cli `planPostFiles` **无条件**含 post.file（封面/主文件）job；**无 download_file 消费**（grep cli.js 无该开关）——**勾选不生效（恒下载封面）** |

**差异影响**：前端勾选「不保存作者索引 / 不下载封面」在我们后端无效——行为固定为「写索引 + 下载封面」。若用户依赖该开关（省流量/省目录），需：①adapter 创建 spec 透传两字段（存 spec_json）②cli downloadAuthor 读 spec 决定 writeCreatorIndex 与 planPostFiles 的 file 项。

## 五、顺带发现：任务卡 running（调度器 UNIQUE 冲突——2026-09-30 新调度器的 bug）

- 现象：task-mun08gxi-ywop6a status=running 但无下载进程、progress 10s 无变化、active_downloads 残留；8790 日志 `[scheduler task-mun08gxi-ywop6a] 执行异常: UNIQUE constraint failed: task_attempts.task_id, task_attempts.sequence`。
- 链路：任务第一次运行 attempt sequence=1（18:23 启动，后被中断 status=interrupted）→ 用户 resume/调度器再次启动 → `downloadTask` 调 `startAttempt(taskId, 1, ...)`（core.js:421 **固定 sequence=1**）→ 与已存在 attempt(sequence=1) **UNIQUE 冲突** → startAttempt 在 try 块**外**（core.js:420-421 在 `try` 之前）→ 异常直接冒泡（不走 catch）→ `[scheduler] 执行异常` 打印 → 任务状态停留 running（420 已 updateTaskStatus('running')）→ **卡死**。
- 原版对照：start_attempt 的 sequence = `MAX(sequence)+1`（webui/task_store.py:337）——**无此问题**。
- 修复：`startAttempt` 的 sequence 改为按任务 `MAX(sequence)+1` 自增（对齐原版）；且把 startAttempt 移入 try（或异常时 `updateTaskStatus('failed')`）防卡 running。

## 六、结论

1. **0 B** = cli job.progress 事件 `size` 字段恒 null 的 bug（emit 用了不存在的 `p.size`，实际字节在 `p.doneBytes`）——transferred 增量分支永不执行。
2. **932 MiB** = total_bytes 正常（job.progress 的 totalSize 累计和，已完成文件大小之和）——**与 0 B 并存是「total 通了、transferred 断了」的 bug 组合**。
3. **两开关**：原版 save_creator_indices/download_file 真实生效；我们创建 spec 丢弃两字段、cli 不消费——恒「写索引+下封面」。
4. **卡 running**：调度器时代 startAttempt 固定 sequence=1 + try 外 → 重跑任务 UNIQUE 冲突 → 卡死。
